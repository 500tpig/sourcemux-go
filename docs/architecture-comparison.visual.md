当前 SourceMux 按事先写好的步骤搜资料、读网页，整理后返回。smartsearch 的 research 还会请 JEV 判断：资料够不够，下一步还该查什么。建议保留现有搜索和读取功能，逐步补上这种判断能力。

## A 三种能力，各司其职

| 能力 | 输入 | 输出 | 对应角色 |
| --- | --- | --- | --- |
| 搜索与抓取 | 查询词或 URL | 链接、摘要、网页正文 | Grok、Exa、Jina 等渠道 |
| JEV 判断 | 问题、候选动作、证据预览 | 用概率回答程序提出的判断题 | TypeSafe System One |
| 答案综合 | 问题和证据 | 有来源的文字答案 | 独立的 reasoning 模型，负责把资料写成答案 |

例如，程序可以问 JEV「现在是否值得用 Exa 搜索」。JEV 返回判断，程序再决定是否执行。允许哪些操作、最多执行几次，都由程序控制。

## B 当前 SourceMux：一个核心，两个入口

```flow
终端 CLI -> 共享任务流程
AI 客户端 MCP -> 共享任务流程
单个 JSON 配置 -> 共享任务流程
共享任务流程 -> 执行路由
执行路由 -> 服务商适配器
服务商适配器 -> 网络客户端
网络客户端 -> 搜索与抓取服务
共享任务流程 -> 独立答案综合
```

人从终端输入命令，走 CLI；AI 调用工具，走 MCP。之后都使用同一套流程。图中的「适配器」把请求和结果转换成各家服务能理解的格式。

默认搜索顺序是 Grok → TinyFish → Exa → Tavily。第一家成功就返回。暂时错误可以换下一家，永久错误或取消会停止。

## C 当前研究：一次固定流程

```flow
研究问题 -> 固定模板生成查询
固定模板生成查询 -> 有限并发搜索
有限并发搜索 -> 链接去重与排序
链接去重与排序 -> 读取选中网页
读取选中网页 -> 摘句与缺口记录
摘句与缺口记录 -> ResearchPack 证据包
ResearchPack 证据包 -> smart-answer 综合答案
```

research 返回一份资料包，里面有来源、摘要和仍未解决的问题。smart-answer 会再把它交给独立模型写成答案。当前研究读完这一批资料后就结束，不会发现内容不足便自动再搜一轮。

`confirmed_facts` 是规则抽取的相关句子，不代表完成独立事实核查。GitHub 抓取主要返回仓库信息和 README；blob 链接还会读取目标文件。

## D smartsearch：公共执行核心与多个入口

```flow
终端与 Agent Skill -> Python CLI 核心
原生桌面 App -> JSON 行协议
JSON 行协议 -> Python CLI 核心
本机配置网页 -> 公共配置接口
公共配置接口 -> Python CLI 核心
Python CLI 核心 -> 候选与研究控制程序
候选与研究控制程序 -> JEV 判断服务
候选与研究控制程序 -> 搜索与正文渠道
候选与研究控制程序 -> 可选独立综合模型
本地健康记录 -> 候选与研究控制程序
```

桌面 App 控制单独安装的 CLI，两者用自己的消息格式通信。这种格式不是 MCP。smartsearch 还允许环境变量覆盖文件中的设置，并把故障记录存到文件，下次运行时仍可使用。

## E smartsearch 研究：根据证据继续

```flow
问题与有限候选 -> JEV 选择动作
JEV 选择动作 -> 并发搜索或读正文
并发搜索或读正文 -> 记录正文与来源
记录正文与来源 -> {证据足够？}
{证据足够？} -> 整理证据与可选综合: 是
{证据足够？} -> {还有预算和新动作？}: 否
{还有预算和新动作？} -> 构造有限缺口候选: 是
构造有限缺口候选 -> JEV 选择动作
{还有预算和新动作？} -> 返回部分证据与停止原因: 否
```

「缺口」就是资料中还没回答的部分。程序根据原问题、子问题和预设模板，准备下一步可用的查询，JEV 从中选择。最终的正式引用只收实际读过的正文，搜索摘要只能作线索。

普通 search 只选一次路，不跑这个研究循环。`deep` 命令只生成离线计划；`research` 才执行研究。默认 JEV 预算是 3 轮、每轮 3 个操作；deep 的 10 轮是上限。

## F 两个项目，差别在哪里

| 维度 | SourceMux 现状 | smartsearch 参考实现 |
| --- | --- | --- |
| 默认搜索 | 固定服务顺序与兜底 | JEV 先选一家，失败时可换同类服务 |
| 研究控制 | 模板查询与一次收集 | 每轮读完后判断还缺什么，决定是否继续查 |
| 最终答案 | 使用单独配置的推理模型写答案 | 可以另外配置写答案的模型 |
| 配置 | 单文件、显式路径 | 配置文件与环境变量覆盖 |
| 健康状态 | 暂时跳过故障入口，程序退出后不保留记录 | 故障记录存到文件，下次运行仍可使用 |
| 证据边界 | 读取网页，再按代码规则摘句和筛选 | 区分发现线索与已读正文 |
| 额外成本 | 检索、抓取与综合调用 | 按选路、评估等阶段增加 JEV 判断 |

SourceMux 已能按 profile 设置和 URL 类型选择服务。接入 JEV 后，希望增加的是：读过资料再判断不足之处，据此决定下一步。

## G 建议：先验证判断，再增加受限循环

```flow
现有研究证据包 -> 第一步：可选 JEV 评估
第一步：可选 JEV 评估 -> 第二步：有上限的补搜
第二步：有上限的补搜 -> 复用现有搜索和抓取
复用现有搜索和抓取 -> 复用独立 reasoning 综合
```

这只是接入建议，尚未实施。先让 JEV 判断现有资料是否够用，确认判断可靠后，再让程序按判断继续搜索。原来的默认流程保留；JEV 使用单独的连接设置。

程序需要规定允许调用哪些服务、最多查几轮、发几次请求，以及最多等待多久。JEV 判断失败时保留材料，并说明尚无法判断。使用这项能力会把问题和资料片段发送给 TypeSafe。
